# Формат вбудованого claim'а + верифікатор + tool/skill для моделей — дизайн

**Статус:** думання на запит оператора ("про формат треба дуже подумати"). Не рішення — дизайн із відкритими розвилками, які твої.

## 0. Найважливіше, що визначає весь формат

**`⚓` у сирому тексті — це твердження АВТОРА, не вердикт.** Уся суть — не довіряти авторському ⚓, а перерахувати. Тож у сирій формі не можна ставити готовий "зелений" вердикт: raw-claim несе **claim + перевірну адресу**, а `✓/✗/◇` домальовує **верифікатор читача**, коли перерахує. Плутати ці дві речі = зробити ще один authority-cached бейдж (те, що ми критикуємо в BADGES.md).

Отже три стани, не один:
- **сира форма** (в тексті): `автор стверджує X, ось адреса для перевірки` — ще не вердикт;
- **verified** (верифікатор перерахував, адреса збіглась): ✓ — автор не збрехав;
- **refuted / stale / unknown** (не збіглась / світ змінився / клас не підтримано): ✗ / ◇.

"Піздьж" ловиться саме на переході сира→refuted: автор поставив адресу, яка не відтворюється.

## 1. Анатомія формату (кандидат)

```
⟦<class>: <content> ⊨ <address> {<meta>}⟧
```

- **`⟦ ⟧`** — делімітери (наша розмітка; працює в будь-якому тексті, малий ризик колізії).
- **`<class>`** — клас settlement'у: `arith cmp count cite mono sha256 warrant lean stipulation`. Визначає, ЯК перераховувати, і — важливо (урок Codex про ortho-ledger) — який *рівень* валідації claim несе (див. §2).
- **`<content>`** — що стверджується.
- **`⊨`** ("settles to" / turnstile) — семантично чесний роздільник до адреси. Альтернатива — `@` (типовніше). ⊨ каже "осідає в", не "дорівнює".
- **`<address>`** — content-address перевірної цілі. Дві форми:
  - **inline result-hash** `sha256:<nf>` — для self-contained claim'ів (arith/cmp): верифікатор перераховує обидві сторони й порівнює адреси, **CAS не потрібен**;
  - **receipt-CID** `cid:<bafy…>` — для world-claim'ів (count/cite/warrant): верифікатор фетчить квитанцію з CAS, переграє, звіряє. Несе **dependency-digests** (freshness).
- **`{<meta>}`** — опційно: профіль/верифікатор (`church@v0`), ATP, статус-рядок ledger'а.

Приклади:
```
⟦arith: 74+1=75 ⊨ sha256:e0419cc5…⟧              (self-contained, CAS не треба)
⟦count: /Теза/ in README.md = 12 ⊨ cid:bafy… ⟧     (world-claim, receipt на CAS, з digest файла)
⟦warrant: PR-42 accepted ⊨ cid:bafy… ⟧             (warrant-запис, re-executable check)
⟦lean: Flourishing⇒Reachable ⊨ sha256:… {KERNEL_DERIVED}⟧
```

## 2. Статус-тип мусить їхати з claim'ом (Codex ortho-ledger)

Одна ⚓ не може злити `KERNEL_DERIVED / IMPLEMENTATION_CONFORMANT / DOMAIN_ADEQUATE`. Клас *імплікує* рядок ledger'а, і верифікатор показує який:
- `arith/cmp/count/cite/sha256` → **IMPLEMENTATION-verifiable** (перерахунок збігається);
- `lean:` → **KERNEL_DERIVED** (Lean-ядро перевірило виведення — але НЕ adequacy);
- `warrant:` → **re-executable з authority-caveat** (integrity+replay, не truth/justice);
- `stipulation:` → **DOMAIN_ADEQUATE=unknown** (формалізовано, адекватність не встановлена).

Тобто ✓ від верифікатора завжди має підпис "✓ *чого саме*" — не голе "passing".

## 3. Що саме адресує `⊨` (розвилка, яку треба вирішити)

- **(a) result-hash** нормальної форми — мінімально, trustless-перерахунок будь-де, але тільки self-contained.
- **(b) receipt-CID** повної квитанції (deps, atp, ski_checks, digest входів) на CAS — self-contained і dependency-bound, але потребує доступності CAS.
- **(c) обидва** — inline result-hash для чистих + receipt-CID для world-claim'ів; клас каже, який застосовний.

**Рекомендація:** (c). Freshness (F3/F4) вимагає, щоб world-claim ніс digest входу — інакше зелена адреса на застарілому файлі. Для count/cite receipt-CID мусить в'язати digest файла; при перерахунку зміна файла → інший digest → STALE, не тихо-зелене.

## 4. Верифікатор ("хромовська приблуда") — три поверхні, один код

Один портативний верифікатор (ts-sigma-ядро + fetch-from-CAS), доставлений трьома способами:
1. **Браузерне розширення** — сканує будь-яку сторінку на `⟦…⟧`, парсить, для self-contained перераховує client-side (Web Crypto), для world-claim фетчить receipt/deps з CAS (IPFS-гейтвей або локальний нод) за CID і переграє, накладає ✓/✗/◇ overlay inline. Це "будь-яка сторінка інтернету".
2. **Букмарклет** — те саме без встановлення, для разового.
3. **Хостована сторінка** — "встав claim → вердикт" (розширення `replayable-badge`).

Чесна довіра розширення: воно довіряє (а) власному коду, (б) що CAS резолвить CID у незмінений байт (content-addressing це гарантує), (в) для URL/file-входів — поточному фетчу (може сказати лише "істинно проти ЦЬОГО фетчу зараз").

## 5. Для моделей: tool + skill (дві різні речі)

**Tool (MCP, розширення наявного `settle_mcp`):** дві дії —
- `emit(class, content)` → розраховує і повертає **готову вбудовувану** `⟦… ⊨ address⟧` (модель вставляє в текст);
- `verify(embedded)` → парсить, перераховує, повертає вердикт ✓/✗/◇ + рівень ledger'а.
(Уже є `settle_text/verify_receipt/check_freshness/check_taint` — це їхня переупаковка під формат.)

**Skill (Claude Code / агентний) — це ДИСЦИПЛІНА, не інструмент:**
- коли модель **пише** текст: маркувати перевірні claim'и форматом і `emit`-ити (не ставити ⚓ без re-executable адреси);
- коли модель **читає** текст із `⟦…⟧`: `verify` перед тим, як вірити (не приймати чужий ⚓ як свій);
- ніколи не стверджувати settled без адреси, яку інший може переграти.

Це буквально Теза 7 як звичка: чорний конус вбудований у те, *як* модель пише й читає, а не пост-фактум. Skill викликає tool; tool робить обчислення.

## 6. Відкриті розвилки (твої рішення — "гарненько продумати")

1. **Глиф/роздільник:** `⟦ ⊨ ⟧` (семантично чесно, але ⊨ важко набрати) vs `⟦ @ ⟧` (типовніше) vs щось ASCII-only для max-портативності (напр. `[[arith: 74+1=75 |= sha256:...]]`).
2. **Що адресує ⊨:** (a)/(b)/(c) з §3 — рекомендую (c).
3. **CAS-субстрат:** IPFS (глобальний, але залежить від гейтвеїв/pinning) vs простий наш content-store vs git-як-CAS. Впливає на "працює скрізь".
4. **Чи ставить автор глиф вердикту взагалі:** сира форма нейтральна (тільки адреса, верифікатор домальовує) — рекомендую; або автор ставить ⚓-as-claim, явно "unverified until recomputed".
5. **Freshness для URL/file-входів:** receipt в'яже digest — але для живого URL "істина" лише проти поточного фетчу; як це показувати чесно.

## 7. Чесна межа (проти overclaim)

Формат **не робить claim'и надійними — він робить брехню виявною.** Вбудований ⊨ не є доказом; це author-claim + перевірна ціль. Довіра переміщується (принцип Codex) до "перерахуй адресу сам" — і content-addressed CAS + портативний верифікатор роблять це можливим будь-де, крім санітизованих поверхонь (README), де лишається лише текстовий ⊨, який перевіряється деінде. Не "trustless embed" — **"вбудова, що робить брехню детектовною звідусіль".**

**Одним рядком:** raw-форма несе claim + перевірну адресу (не вердикт); клас несе рівень ledger'а; ⊨ адресує result-hash (self-contained) або receipt-CID з digest-входів (world/freshness); один портативний верифікатор у трьох формах (розширення/букмарклет/сторінка) ловить "піздьж" перерахунком; для моделей — tool (emit/verify) + skill (дисципліна писати/читати через settlement). Розвилки §6 — твої.
