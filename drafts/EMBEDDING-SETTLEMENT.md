# Як вбудувати розраховуваний терм у текст (README, будь-де в інтернеті) — дослідження

**Статус:** дослідження на запит оператора. Не рішення — карта варіантів із чесними межами.
**Питання:** як вставити наш терм/warrant у README чи інший текст так, щоб claim (чи "піздьж") у прозі був **розраховуваним** — і щоб працювало не в межах файла/репо, а взагалі в інтернеті.

## 0. Ядро відповіді (найважливіше, решта — UX над ним)

**Claim стає розраховуваним тоді, коли він несе свій settlement як content-address.** Не "живий бейдж", а **вбудований хеш**: речення `74+1=75 [⚓ e0419cc5…]`, де `e0419cc5` — content-address нормальної форми (AIE). Різниця між істиною і "піздьжем" тоді = "чи перерахований хеш збігається з вбудованим". Текст нічого не *виконує* — він **несе** хеш; обчислення робить будь-хто, кому не байдуже, портативним верифікатором (ts-sigma — 30 рядків, браузерно-нативний).

Це settlement-дисципліна, застосована до прози: **речення з вбудованим settle-хешем — це речення, яке можна спіймати на брехні, звідки завгодно, назавжди, крихітним верифікатором.** Content-addressing робить це trustless (за модулем SHA-256) і **repo-незалежним** — хеш не прив'язаний до того, де лежить текст.

Warrant — це вже готова форма цього: warrant-запис content-addressed і перевиконуваний (`ski@v1`). Тож "вбудувати warrant у текст" = вбудувати його CID; читач резолвить (warrant-store / IPFS) і переганяє check. Warrant = запис; вбудова = CID-посилання; верифікатор = портативний.

## 1. Жорстке обмеження, що визначає все: де рендериться текст

| Поверхня | JS? | Живий HTML? | Що можна |
|---|---|---|---|
| **GitHub README** | НІ (санітизується) | майже ні (allowlist тегів, без `<script>`, без `<style>`, без `<object>/<iframe>`) | лише `<img>` з ендпоінта + текст |
| **Хостована сторінка** (GitHub Pages, наш сайт) | ТАК | ТАК | повна клієнтська верифікація |
| **Будь-яка сторінка в інтернеті** | залежить від сайту | — | лише через код, що виконує **читач** (розширення/букмарклет) |

Наслідок: **у GitHub README неможлива жива клієнтська верифікація.** Крапка. Можна тільки (а) серверний SVG-бейдж як `<img>`, або (б) вбудований content-address як **текст**, що його читач перевіряє окремим інструментом. Живе — тільки на хостованій сторінці або через розширення читача.

*(SVG-нюанс: SVG, завантажений через `<img>`, НЕ виконує вбудований `<script>` — браузери не запускають скрипти в img-SVG. SVG зі скриптом працює лише через `<object>/<iframe>`, які GitHub санітизує. Тож "SVG, що рахує сам себе в README" = ні; "SVG-бейдж, порахований сервером-ендпоінтом і вставлений як img" = так. Ці межі — відома поведінка GitHub-санітайзера; звірити з актуальним allowlist.)*

## 2. Рівні рішення (від repo-локального до всеінтернетного)

### Рівень 0 — Серверний SVG/PNG-бейдж (працює в GitHub README)
`![settled](https://<our-endpoint>/settle?claim=<...>)` — ендпоінт при фетчі **перераховує** claim (наш settle_gate) і повертає SVG ⚓/✗ із CID квитанції. Модель shields.io, але з нашим settlement.
- **Плюс:** єдине, що рендериться *inline* у санітизованому README.
- **Мінус (за нашим же BADGES.md):** authority-cached на відстані — читач довіряє **нашому серверу**, це не клієнтський replay. Чесно: бейдж — це *вказівник* на settlement, порахований нашим оракулом; CID у бейджі дає скептику змогу переграти деінде.

### Рівень 1 — Вбудований content-address як текст (repo-незалежний, trustless)
Claim у прозі несе settle-хеш (див. §0). Нічого не рендериться живо, але **будь-хто** перевіряє портативним верифікатором. Найаліґнедніший: trust relocation → "перерахуй хеш сам", а не "вір серверу".
- Формат-кандидати: `⟦arith: 74+1=75 ⚓@e0419cc5⟧` (наша ґейт-розмітка + пін), або warrant-CID `[warrant:bafy…]`.

### Рівень 2 — Жива клієнтська верифікація (хостована сторінка, НЕ README)
Уже побудовано: `ts-sigma/replayable-badge.html` — claim переосідає в **браузері читача** (Web Crypto), бейдж зелений бо *ти* перевірив. Працює на GitHub Pages / нашому сайті. README на це не здатен — тільки хостована HTML.
- Тобто: публікувати доки як **Pages (HTML)**, не як сирий README, і там settlement живий клієнтський.

### Рівень 3 — Через увесь інтернет, на будь-якій сторінці (найамбітніше)
Щоб claim був розраховуваним на *чужій* сторінці, код мусить виконувати **читач**:
- **Браузерне розширення / букмарклет**, що сканує будь-яку сторінку на нашу розмітку (`⟦…⟧` або `data-`-атрибут або спец-хеш), витягує content-address, фетчить потрібний term/store із **CAS (IPFS/наш store)** за хешем, і переганяє верифікацію client-side (ts-sigma) — накладаючи ⚓/✗ overlay. Це перетворює "піздьж" на видимий вердикт на *будь-якому* сайті для кожного, хто має розширення.
- **CAS/IPFS-якорення:** квитанція + її залежності живуть за CID; claim у тексті посилається на CID; будь-хто резолвить (IPFS-гейтвей або локальний нод) і переганяє. Це repo-незалежний субстрат — receipt адресований у глобальній content-addressed мережі, незалежно від того, де текст.

## 3. Архітектура, що відповідає "все, через інтернет"

Складається з трьох незалежних шарів (коса, не стек):
1. **Claim несе settlement як content-address** (§0) — портативне, repo-незалежне, trustless ядро.
2. **Контент (terms/store/deps) живе в content-addressed мережі** (IPFS або CAS з CID) — верифікатор фетчить за хешем звідусіль.
3. **Верифікатор клієнтський і портативний** (ts-sigma, браузерно-нативний) — доставка: (a) хостована сторінка, куди вставляєш claim; (b) розширення, що авто-сканує будь-яку сторінку; (c) CLI. Один верифікатор, різні поверхні.
4. **Для поверхонь без JS (GitHub README):** деградація до серверного SVG-бейджа-вказівника (Рівень 0), чесно про relocation, з CID у бейджі для скептика.

## 4. Чесна межа (проти overclaim — урок сесії)

Жодна вбудова **не робить довіру непотрібною — вона її переміщує** (принцип Codex: формалізація/адресація зсуває розрив, не закриває). Найаліґнедніша вбудова зсуває до "перерахуй content-address сам" (trustless за модулем SHA-256), і content-addressed-web + портативний-верифікатор роблять це можливим *будь-де*. README-image-шлях зсуває до "вір нашому ендпоінту" — слабше, але єдине, що рендериться inline в санітизованому README. І: розширення довіряє тому, хто його написав; CAS-фетч довіряє, що CID резолвиться в незмінений байт (content-addressing це і гарантує). Тобто не "trustless embed", а **"вбудова, що робить свою довіру явною і вердикт перевиконуваним звідусіль"**.

## 5. Рекомендований шлях (мінімальний, по одному вкушеному кроку)

1. **Формат вбудованого claim'а** — зафіксувати: `⟦клас: вміст ⚓@<cid>⟧` (розмітка ґейта + content-address пін). Це Рівень 1, працює як текст будь-де.
2. **Портативний верифікатор** — розширити наявний `replayable-badge`/ts-sigma у "встав claim → вердикт" (Рівень 2), і як CLI. Один код.
3. **Розширення/букмарклет** (Рівень 3) — коли Рівень 1–2 стабільні; авто-скан будь-якої сторінки. Це і є "через увесь інтернет".
4. **CAS/IPFS** для term/store за CID — субстрат, що відв'язує від репо.
5. **README-бейдж-ендпоінт** (Рівень 0) — останнім, як deградація для GitHub-inline, з чесним "authority-relocated" маркером.

**Одним рядком:** розраховуваність вбудовується не живим кодом у тексті (README цього не дасть), а **content-address'ом, що подорожує з claim'ом**; портативний клієнтський верифікатор (ts-sigma) + content-addressed store (IPFS) роблять його перевірним будь-де; браузерне розширення — це "будь-яка сторінка інтернету"; а для санітизованого README лишається лише серверний бейдж-вказівник, чесно позначений як relocated-trust.
